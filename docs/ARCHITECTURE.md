# Архитектура

## 1. Два продукта, одна модель

```
                    ┌──────────────────────────────┐
                    │  H = h − N + C + Δ           │
                    └──────────────┬───────────────┘
                                   │
            ┌──────────────────────┴──────────────────────┐
            │                                             │
   ┌────────▼─────────┐                         ┌─────────▼──────────┐
   │ libbaltic        │                         │ baltic_embedded    │
   │ (host / server)  │                         │ (MCU / Cortex-M)   │
   ├──────────────────┤                         ├────────────────────┤
   │ PROJ vgridshift  │                         │ integer bilinear   │
   │ GeoTIFF / GTX    │                         │ int16 grid in Flash│
   │ files, heap      │                         │ no heap, no OS     │
   │ CLI, calibration │                         │ fixed Δ, host calib│
   └──────────────────┘                         └────────────────────┘
```

Обе реализации считают одну и ту же величину. Различаются источником
`N` и вычислительной средой.

## 2. Полная библиотека

### Слои

```
baltic/baltic.h                 публичный API
src/baltic.c                    контекст, валидация, Δ, калибровка
        │
        ├── PROJ context #1 ── vgridshift(EGM2008) ── GeoTIFF/GTX
        └── PROJ context #2 ── vgridshift(correction) ── GeoTIFF/GTX
```

Для геоида и поправочной сетки создаются **отдельные контексты PROJ**.
Причины:

- PROJ ищет `+grids=<basename>` по своему search path; два контекста
  исключают коллизию одинаковых имён файлов из разных каталогов;
- каталоги с пробелами поддерживаются: в `+grids=` передаётся только
  basename, а каталог добавляется в search path;
- ошибки и кэш сеток не смешиваются.

### Конвейер

```
lat/lon/h (градусы, метры)
        │
        ▼
+proj=pipeline
  +step +proj=unitconvert +xy_in=deg +xy_out=rad
  +step +proj=vgridshift +grids=... +multiplier=1
  +step +proj=unitconvert +xy_in=rad +xy_out=deg
```

Соглашение о знаке:

- forward `vgridshift` = `H → h` (добавляет `N`), это EPSG:3855 → EPSG:4979;
- inverse `vgridshift` = `h → H` (вычитает `N`).

Для `h → H` библиотека вызывает inverse, для `H → h` — forward.
Поправочная сетка `C` добавляется к `H`:

- forward — `H → H + C`;
- inverse — `H → H − C`.

### Контекст

`baltic_ctx` хранит:

- два PROJ-контекста и две операции;
- `Δ` под мьютексом;
- метаданные геоидной сетки;
- абсолютные пути (для диагностики).

Создание контекста:

1. проверка аргументов;
2. поиск файла (cwd, затем `grid_search_path`);
3. чтение заголовка сетки через `proj_grid_info`;
4. создание PROJ-контекстов с отключённой сетью;
5. создание пайплайнов;
6. освобождение всех ресурсов при любой ошибке.

### Потоки и ошибки

- Все вызовы `proj_trans` сериализуются мьютексом контекста.
- `baltic_convert_batch` держит мьютекс на весь массив.
- Ошибки — enum `baltic_status`; подробности последней ошибки —
  thread-local `baltic_last_error()`.
- Точка вне покрытия — `BALTIC_ERR_OUT_OF_GRID`, а не «нулевая высота».

### Калибровка

`baltic_calibrate_offset` считает `H_model = h − N + C` без `Δ`,
накапливает `r_i = H_known − H_model`, возвращает среднее и RMS.
Контекст не изменяется: решение применить `Δ` остаётся за вызывающим
кодом.

## 3. Встраиваемая библиотека

### Генерация данных

```
EGM2008 GeoTIFF
      │  host: egm2008_to_c (полная libbaltic)
      ▼
region crop + resample
      │
      ▼
int16_t values[]  (мм относительно base_mm)
const baltic_embedded_grid descriptor
```

Генератор:

- сэмплирует `N` в узлах региона через полную библиотеку;
- округляет до миллиметров;
- выбирает `base_mm` так, чтобы размах помещался в `int16`;
- проверяет, что размах ≤ 65.534 м;
- пишет `.c`/`.h` с `const`-массивом в секции `.baltic_grid`.

### Формат сетки

```
values[iy * width + ix] = N(lon,lat) − base_mm
lon = lon_min_u6 + ix * lon_step_u6
lat = lat_min_u6 + iy * lat_step_u6
```

- строка 0 — южная;
- квантование 1 мм;
- шаг и границы — микроградусы;
- выравнивание 32 байта (кэш-линии Cortex-M7).

### Интерполяция

Билинейная, fixed-point Q8:

1. координата → индекс ячейки (`ix`, `iy`) и дробная часть (`fx`, `fy`;
   0…256);
2. значения смещаются на `+32768`, чтобы все промежуточные величины были
   неотрицательными;
3. два горизонтальных прохода и один вертикальный, деление на 256
   заменено сдвигом;
4. обратное смещение и `+ base_mm`.

Диапазоны подобраны так, чтобы промежуточные произведения помещались в
`int32_t`. Переполнение итоговой высоты проверяется через `int64_t` и
возвращает ошибку.

### Память и среда

- нет `malloc`, `memcpy`, `libm`, файловых операций;
- нет глобального изменяемого состояния;
- сетка и дескриптор — `const`, обычно во Flash;
- `.data/.bss` — 0, стек ≈100 Б;
- код 846–880 Б на M0+/M4, 868 Б на M7 (`-O2`).

## 4. Границы применимости

| Вопрос | libbaltic | baltic_embedded |
|---|---|---|
| Покрытие | весь мир | один регион |
| Источник сетки | файл | `const` массив |
| Точность `N` | double, интерполяция PROJ | 1 мм, fixed-point |
| `Δ` | калибровка в рантайме | передаётся готовым |
| Региональная `C` | вторая сетка | вторая сетка (опционально) |
| Сеть/файлы | сеть отключена, файлы нужны | нет |
| ОС/heap | да | нет |
| Потоки | мьютекс | реентерабельно, без блокировок |

## 5. Решения и компромиссы

- **Почему PROJ, а не своя интерполяция в полной версии?** ГеoTIFF,
  GTX, поиск сеток, соглашение о знаке и обработка краёв уже проверены
  в PROJ; дублировать это рискованно.
- **Почему отдельная embedded-версия, а не урезанный PROJ?** PROJ — C++,
  libtiff, SQLite, файловая система; для MCU это неоправданно. Формат
  сетки и целочисленная интерполяция дают <1 КБ кода.
- **Почему int16 мм с базой?** 2 байта на узел и 1 мм точности; размах
  региона обычно много меньше 65 м. Для глобальной сетки нужен другой
  формат.
- **Почему `Δ` не калибруется на MCU?** Для калибровки нужны контрольные
  пункты и статистика; это задача хоста. На устройство передаётся одно
  число.
